## ai分析

1. ZJU DDL、当前日程、跨天日程  
   这三个问题很可能属于同一套时间模型。Android 的当前时间保存为 UTC `Z` 字符串，而普通日程是无时区本地字符串，却直接在 SQLite 中进行字符串比较；后端 ZJU 时间转换又依赖运行机器的系统时区。此外，日程范围查询采用“完整包含”，跨天事件会被排除。建议统一为 UTC 存储、北京时间展示，并把范围条件改为区间相交：

   ```text
   start_time < 查询结束
   end_time > 查询开始
   ```

2. 项目的“下一步做”  
   原因已经明确：后端待办按 `created_at DESC` 返回，然后直接选第一个未完成项，所以实际上偏向“最后加入项目的待办”。建议增加 `position/sort_key`，默认按“手动顺序 → DDL 升序 → 创建时间”选择，并支持拖动调整。

3. 任务完成后复活、今日完成不显示  
   当前完成操作分两次写入：先修改待办，再更新今日日志。如果第二步失败，待办其实已完成，但页面不会重新加载，看起来就像“复活”；并发完成多个待办时，日志数组还有最后写入者覆盖风险。建议增加一个原子化“完成待办并记录到今日日志”接口，在同一事务中完成两件事。

4. 地点备注和短时段文字  
   ZJU 课程导入已经把 `item.location` 写入日程，主要缺口是视图没有展示：日视图只显示备注，周视图只有时间和标题。建议短事件采用密度分级：

   - 很短：只显示标题
   - 中等：标题 + 时间
   - 较长：标题 + 时间 + 地点/备注

5. DDL 12/24 小时制  
   当前 `datetime-local` 的显示受操作系统和浏览器区域设置控制，无法稳定由应用切换。若要支持，需要设置项加自定义时间输入与格式化器；不涉及数据模型，可放 v0.9 体验完善。

6. 备份导入与删除  
   当前逻辑是安全的“按 UUID 合并、导入包优先、未出现的本地数据保留”，不会执行删除。v0.8 建议明确拆成：

   - 合并导入：永不删除本地数据。
   - 完整恢复：先自动备份当前数据库，预览将新增、覆盖、删除的数据，再进行事务化替换。

7. 计时取消卡住  
   Web/桌面端静态代码里的取消状态流本身看起来正确；但 Android 本地数据层明确尚未实现计时后台流程。如果问题发生在 Android，这就是直接原因；如果发生在桌面端，则需要带平台和操作步骤复现。修复时建议无论成功失败都重新请求 `/timer/current`，并给操作按钮加执行锁，避免前端状态残留。
