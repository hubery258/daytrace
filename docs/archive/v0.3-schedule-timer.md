# v0.3.x 日程体验与计时设计

## 版本定位

v0.3.x 的目标是把日迹的日程能力从“能记录计划和实际”升级为“适合日常规划、执行计时和复盘对照”。

当前日程页已经有计划日程与实际记录的共轴对照，这是日迹区别于普通 todo 工具的重要能力。v0.3.x 要在这个基础上补齐三件事：

- 通过计时自然生成实际日程。
- 通过拖拽时间轴更快创建日程。
- 通过更好的日期、周视图、月视图浏览较长时间范围。

这个阶段仍然服务于个人效率闭环，不做复杂日历软件，也不做多人共享日历。

## 产品目标

- 用户可以在计时页开始、暂停、继续、结束一次计时。
- 计时结束后可以生成一条实际日程记录。
- 用户可以在日程时间轴上拖拽选择时间段，并直接创建计划日程或实际记录。
- 日程页日期跳转更顺手。
- 用户可以从日视图扩展到周视图和月视图。
- 计划日程、实际记录、项目、待办之间保持清晰关系。

## 核心场景

### 正在做一件事

用户开始写代码或写作业时，打开计时页，选择或输入当前事项，开始计时。结束后，系统生成实际日程，进入日程页右侧实际记录。

### 临时补录实际记录

用户忘记计时，但事后想补录，可以在实际记录时间轴上拖拽一段时间，创建实际日程。

### 快速安排计划

用户在计划日程时间轴上拖拽 14:00-15:30，创建一个计划日程，不必先打开表单再手动输入开始和结束时间。

### 周期性回看

用户想看这一周每天大概做了什么，进入周视图；想看本月课程、项目和重要 DDL 分布，进入月视图。

## 核心产品规则

### 计划日程与实际记录

- 计划日程表示“我打算怎么安排时间”。
- 实际记录表示“我实际上怎么使用时间”。
- 计时生成的是实际记录，不是计划日程。
- 拖拽创建时，用户在哪一列拖拽，就默认创建对应类型：计划列创建计划日程，实际列创建实际记录。
- 过去日期的计划日程仍不建议修改；实际记录允许补录和修改。

### 计时与实际记录

v0.3.x 计时能力先服务于生成实际日程。

建议规则：

- 同一时间只允许一个进行中的计时。
- 计时必须支持暂停和继续。
- 计时结束后必须先进入确认表单，用户可以修改名称、项目、关联待办、开始时间、结束时间、备注。
- 用户确认后才生成实际日程。
- 用户取消计时时，不生成实际日程。
- 如果计时时长过短，结束时提示用户是否仍然保存。

### 计时持久化

计时状态应该尽量可靠。

v0.3.0 使用后端保存计时会话，而不是只存在前端内存。这样刷新页面后仍能恢复当前计时。

前端可以用 `localStorage` 做临时显示缓存，但不能作为唯一状态来源。

### 时间粒度

v0.3.x 第一版采用 15 分钟粒度：

- 拖拽选择时吸附到 15 分钟刻度。
- 表单仍允许用户手动调整到任意分钟。
- 后续可以在设置中允许用户选择 5/10/15/30 分钟粒度。

### 重叠日程

产品倾向是不允许重叠，因为重叠会让时间轴卡片难以阅读，也会削弱计划/实际对照的清晰度。

但当前版本已有日程逻辑可能默认允许重叠，因此 v0.3.0 采用渐进处理：

- 创建或编辑日程时必须检测同列同日期的时间重叠。
- 如果检测到重叠，必须给出明确提示。
- 如果前端能够把重叠卡片展示清楚，可以允许用户确认后继续创建。
- 如果暂时无法可靠展示重叠卡片，则不允许创建重叠日程。
- 无论是否允许保存，重叠情况都不能导致卡片完全遮挡、文字混乱或无法点击。

这条是 v0.3.0 的重要验收点：要么处理好重叠展示，要么阻止重叠创建。

### 项目联动

v0.3.x 应继续支持 v0.2 的项目能力：

- 计时结束生成实际日程时，可以选择项目。
- 拖拽创建日程时，可以选择项目。
- 日程块继续展示项目颜色或项目标记。
- 项目详情页中的日程列表应能看到由计时生成的实际记录。

## 功能范围

### 计时页

新增计时页，建议导航中显示为“计时”。

计时页包含：

- 当前计时状态。
- 开始计时入口。
- 暂停、继续、结束、取消操作。
- 当前事项名称。
- 可选项目。
- 可选关联待办。
- 备注。
- 最近计时记录。

计时结束确认表单包含：

- 名称。
- 开始时间。
- 结束时间。
- 项目。
- 关联待办。
- 地点，可选。
- 备注。
- 是否保存为实际记录。

### 日程页拖拽创建

日程页支持在时间轴上拖拽创建日程：

- 在计划列拖拽，默认创建计划日程。
- 在实际列拖拽，默认创建实际记录。
- 拖拽时显示半透明选区。
- 松开后打开日程创建浮层，自动填入日期、开始时间、结束时间、计划/实际类型。
- 拖拽选区默认吸附到 15 分钟粒度。
- 如果拖拽时间过短，至少创建 15 分钟时间段。

### 日期跳转优化

当前日期跳转比较工具化，v0.3.0 应优化为更顺手的日期导航：

- 今日按钮。
- 前一天/后一天。
- 日期选择器。
- 本周日期条，显示周一到周日。
- 当前日期突出显示。
- 有日程的日期做轻量标记。

### 周视图

v0.3.1 建议实现周视图。

周视图目标：

- 快速查看一周内的计划和实际安排。
- 支持点击某天进入日视图。
- 支持显示项目颜色。
- 支持计划/实际切换，避免移动端过度拥挤。

v0.3.1 不必实现：

- 复杂拖拽跨天调整。
- 类似专业日历的冲突排布。
- 多日连续日程。

### 月视图

v0.3.2 建议实现月视图。

月视图目标：

- 查看一个月内的日程密度、课程分布、项目 DDL 和重要事项。
- 支持点击日期进入日视图。
- 支持显示每天少量摘要。

月视图不做完整日历软件，只做复盘和导航辅助。

## 暂不进入 v0.3.x

- 循环日程。
- 日程自动排程。
- 多人共享日历。
- 外部日历订阅。
- 日历导入导出。
- 复杂冲突检测和自动解决。
- 跨天日程的完整交互优化。
- 系统级通知提醒。

系统级提醒放到 v0.5.x；循环日程可以在后续根据实际需求再评估。

## 建议数据模型

### timer_sessions

采用后端保存计时会话，建议新增：

```text
timer_sessions
- id
- name
- status
- project_id nullable foreign key -> projects.id
- linked_todo_id nullable foreign key -> todos.id
- started_at
- last_resumed_at
- paused_seconds
- ended_at
- created_schedule_id nullable foreign key -> schedules.id
- notes
- created_at
- updated_at
```

状态建议：

```text
running
paused
completed
canceled
```

### schedules

当前 `schedules` 表已经用 `is_planned` 区分计划日程和实际记录。v0.3.x 可以继续复用这个模型。

计时结束后创建：

```text
is_planned = false
start_time = timer started_at
end_time = timer ended_at
```

如需追溯计时来源，可以给 `schedules` 增加：

```text
source nullable string  # manual / timer / zju / ai_draft 等
```

这不是 v0.3.0 必需，但有助于后续统计。

## API 建议

新增计时接口：

```text
GET  /api/timer/current
POST /api/timer/start
POST /api/timer/pause
POST /api/timer/resume
POST /api/timer/finish
POST /api/timer/cancel
GET  /api/timer/recent
```

说明：

- `finish` 可以只结束计时并返回会话，也可以同时创建实际日程。
- 更推荐结束后返回确认数据，由前端确认后再调用日程创建接口生成实际记录。
- 如果希望少一次请求，也可以让 `finish` 接收确认后的 schedule payload 并直接生成实际记录。

日程接口建议增强：

- 支持更宽松的日期范围查询，服务周/月视图。
- 支持按项目过滤。
- 支持返回重叠提示所需的同日日程。

## 验收标准

v0.3.0 完成时，应满足：

- 用户能开始一次计时。
- 用户能暂停、继续、结束或取消计时。
- 页面刷新后，当前计时状态不会轻易丢失。
- 计时结束后，用户能确认并生成实际日程。
- 生成的实际日程出现在日程页实际记录列。
- 用户能在计划列拖拽创建计划日程。
- 用户能在实际列拖拽创建实际记录。
- 拖拽创建时，开始和结束时间能正确预填。
- 用户能更方便地跳转日期。
- 原有手动创建、编辑、删除日程仍正常工作。
- 项目关联在计时和拖拽创建流程中可用。

## 风险与注意事项

- 计时功能如果只放前端，刷新、休眠、浏览器关闭都会带来可靠性问题。
- 拖拽创建时间段容易和滚动冲突，移动端要谨慎处理。
- 周视图和月视图容易膨胀成专业日历，应控制展示密度。
- 重叠日程必须检测；如果无法可靠展示重叠卡片，就禁止创建重叠日程。
- 计时生成实际记录后，不要自动修改计划日程，避免破坏计划/实际对照。

## 待确认问题

- 计时是否必须支持暂停/继续？
  - 已确认：必须支持。
- 计时状态是否必须由后端保存？
  - 已确认：后端保存，前端不能只依赖 React state。
- 计时结束后是立即生成实际日程，还是先进入确认页？
  - 已确认：先确认，再生成实际日程。
- 拖拽时间粒度是否采用 15 分钟？
  - 已确认：采用 15 分钟。
- 重叠日程是否允许？
  - 已确认：产品倾向不允许。v0.3.0 如果能把重叠卡片展示清楚，可以允许用户确认后创建；如果处理不好，就必须禁止重叠创建。
- 计时页是否放进顶部导航？
  - 当前建议：放入。
- 周/月视图是否必须在 v0.3.0 完成？
  - 已确认：不放入 v0.3.0，拆到 v0.3.1/v0.3.2。
- 是否需要记录日程来源 `source` 字段，例如 manual/timer/zju？
  - 当前建议：可以做，但不是 v0.3.0 必需。
