# v0.6.x 安卓端与桌面端打包体验版设计

## 版本定位

v0.6.x 的目标是把日迹从浏览器中的本地 Web 应用，推进到安卓端和桌面端的体验版。

这个版本不是正式多端同步版，也不是正式移动端发布版。它的重点是验证：

- 现有产品是否能被打包成更稳定的本地应用形态。
- 安卓端和桌面端的核心流程是否可用。
- 数据能否通过基础导入导出在不同端之间迁移。
- 当前领域模型是否适合未来做账号与多端同步。

v0.6.x 不做系统级提醒，也不做账号同步。

## 产品目标

- 用户能安装并打开桌面端体验版。
- 用户能安装并打开安卓端体验版。
- 核心页面在安卓端和桌面端基本可用。
- 核心数据保存在本地。
- 用户能导出一个逻辑 JSON 数据包。
- 用户能在另一个端导入该 JSON 数据包。
- 导入导出能覆盖当前核心实体，为 v1.1 同步做模型验证。

## 核心原则

- 先体验版，后正式版：v0.6 允许粗糙，但必须验证技术路线。
- 数据模型优先统一：不同平台可以有不同底层存储，但领域模型必须一致。
- 导入导出优先 JSON：不要只依赖复制 SQLite 文件。
- 不提前做同步：导入导出是手动同步雏形，账号同步放到 v1.1。
- 不追求系统级提醒：提醒放到 v1.2，等安卓端/桌面端/同步能力更稳定后设计。

## 推荐推进顺序

建议先做桌面端，再做安卓端。

原因：

- 桌面端更容易复用当前 React + FastAPI + SQLite 架构。
- 安卓端不适合直接依赖 FastAPI 后端，可能需要数据层或运行时方案调整。
- 先完成桌面端可以验证本地应用壳、数据目录、启动流程和导入导出机制。
- 安卓端应先做技术路线验证，不要一开始承诺完整体验。

## 技术路线候选

### 桌面端

候选方案：

1. Electron + FastAPI sidecar
2. Tauri + FastAPI sidecar
3. 纯前端本地存储重构

v0.6 已确认优先采用：Electron + FastAPI sidecar。

原因：

- 能最大程度复用当前后端业务逻辑。
- SQLite 仍可由后端管理。
- 前端改动较少。
- Electron 生态成熟，第一版更适合快速做出可安装、可测试的桌面体验包。

需要验证：

- 如何启动后端 sidecar。
- 如何选择不冲突的本地端口。
- 如何管理 SQLite 数据目录。
- 后端异常退出时如何提示用户。
- 打包体积是否可接受。

### 安卓端

候选方案：

1. Capacitor + WebView + SQLite 插件
2. React Native 重写移动端壳
3. Android 内嵌 Python/FastAPI
4. WebView 连接局域网或远端后端

v0.6 已确认优先采用：Capacitor + WebView + SQLite 插件。不建议优先选择 Android 内嵌 Python/FastAPI。

原因：

- 能较多复用 React 前端。
- 更接近真正本地安卓应用。
- 不需要在 Android 内塞 Python 后端。

但它的代价是：

- 需要为安卓端设计本地数据访问层。
- 现有前端 API 调用假设后端存在，可能需要适配。
- 未来同步需要依赖统一领域模型，而不是依赖同一个 SQLite 文件。

不推荐第一版采用 Android 内嵌 Python/FastAPI 作为长期路线。它可能能跑，但维护和发布风险较高。

### 安卓端技术难点说明

当前 Web 版的典型运行方式是：

- React 前端负责界面。
- FastAPI 后端负责业务逻辑和数据库访问。
- SQLite 作为本地数据库。

桌面端可以比较自然地保留这个结构：Electron 打开前端窗口，同时启动一个本机 FastAPI sidecar，前端继续通过 HTTP 调用后端。

安卓端的困难在于，手机 App 不是一个天然适合长期运行 Python 后端服务的环境：

- Android 不会像桌面系统一样自然地托管一个 Python/FastAPI 常驻进程。
- 后台进程、端口监听、文件目录权限、系统休眠和安装包体积都会增加维护成本。
- 如果强行把 Python 后端塞进安卓包里，第一版可能能跑，但后续升级、崩溃诊断、权限适配和应用商店发布都会更麻烦。
- 如果安卓端绕过 FastAPI 直接读写 SQLite，前端的数据访问方式又需要适配，否则同一套页面不知道该调用 HTTP API 还是本地插件。

因此 v0.6 安卓端的核心任务不是一次性做出完整移动版，而是验证一条可持续的数据路线：

- 尽量复用 React 页面。
- 安卓端通过 Capacitor WebView 承载前端。
- 本地数据通过 SQLite 插件或等价本地数据层访问。
- 领域模型、UUID、导入导出格式与桌面端保持一致。

这样即使桌面端继续使用 FastAPI + SQLite，安卓端改用本地插件访问数据，未来仍然可以通过统一的领域模型和同步协议实现多端同步。

## 数据导入导出

v0.6.x 必须加入基础 JSON 导入导出，用于手动迁移数据和验证未来同步模型。

### 导出格式

建议导出逻辑 JSON 包，而不是直接导出 SQLite 文件。

示例结构：

```json
{
  "app": "riji",
  "schema_version": "0.6.0",
  "exported_at": "2026-07-28T12:00:00",
  "entities": {
    "projects": [],
    "todos": [],
    "schedules": [],
    "daily_logs": [],
    "log_templates": [],
    "timer_sessions": [],
    "recurrence_rules": []
  }
}
```

ZJU 凭据、AI API Key、Cookie、密码等敏感信息默认不导出。

### 导入策略

v0.6.x 第一版可以采用全量导入策略，但必须明确提示用户。

建议支持两种模式：

- 预览导入：展示数据包内实体数量和 schema_version。
- 确认导入：写入本地数据库。

第一版可以先做“追加/合并导入”，但需要防止重复。

如果无法可靠合并，宁可先做“清空本地数据后导入”，并给出强提示。

### 为未来同步铺路

导入导出应尽量采用稳定字段：

- 实体 UUID。
- `created_at`。
- `updated_at`。
- 可选 `deleted_at` 或后续 tombstone。
- 外部导入数据的 `source` / `external_id`。

如果当前数据库仍使用自增 ID，v0.6 可以先在导出层生成稳定映射，但更推荐逐步给核心实体补充 UUID 字段。

## 应覆盖的数据实体

v0.6 基础导入导出至少覆盖：

- 项目。
- 待办。
- 日程。
- 每日总结。
- 日志模板。
- 计时会话。
- 重复规则。

可选覆盖：

- ZJU 导入映射。
- ZJU 校历缓存。
- ZJU 成绩快照。

默认不导出：

- AI API Key。
- ZJU 密码。
- Pintia Cookie。
- Session、token、任何敏感凭据。

## 功能范围

### 桌面端体验版

应支持：

- 启动应用。
- 自动启动本地后端或访问内置服务。
- 使用独立本地数据目录。
- 访问核心页面。
- 创建/编辑待办、项目、日程。
- 今日总结。
- 计时。
- AI 功能仍依赖用户本地浏览器/应用配置的 API Key。
- 数据导入导出。

### 安卓端体验版

应支持：

- 安装和启动。
- 核心页面可以浏览。
- 最初 MVP 已实现的核心功能不能缺少。
- 至少能验证待办、日程、项目和今日总结的本地读写路线。
- 数据导入导出。

安卓端第一版可以不完整支持：

- ZJU 集成。
- AI 功能。
- 复杂日程拖拽。
- 计时后台运行。

这些能力是否进入安卓端 v0.6，需要视技术路线验证结果决定。
### 安卓端 MVP 核心功能验收清单

归档的 `mvp.md` 更像早期事项清单，其中部分想法已经被后续版本替代。v0.6 安卓端的 MVP 核心功能应以当前产品主流程为准：保证日迹作为个人效率工具能在安卓端跑通，而不是保证 ZJU、AI、复杂交互全部完整。

安卓端不能缺少：

- 首页核心信息浏览：当前日程、关注任务、临近 DDL、等待答复和项目入口至少可用。
- 待办基础闭环：创建、编辑、完成、删除、DDL、提醒天数、分类、关注、等待答复和备注。
- 项目基础闭环：创建、编辑、状态、DDL、颜色、描述/备注；待办和日程可以归属项目。
- 日程基础闭环：创建、编辑、删除计划日程和实际记录，支持开始时间、结束时间、地点、备注和项目归属。
- 今日总结基础闭环：查看当天完成待办，填写和保存今日日志。
- 数据本地保存：安卓端关闭重开后核心数据仍存在。
- 基础 JSON 导入导出：能导出核心个人数据，也能从 JSON 导入并恢复核心数据。

安卓端 v0.6 可以暂不完整支持：

- ZJU 学习任务、Pintia、课表、成绩和学分概览。
- AI 总结和 AI 新建。
- 日程拖拽创建、周视图、月视图等复杂日程交互。
- 计时后台运行。
- 重复规则的完整移动端编辑体验。
- 页面/模块自定义开关。
- 系统级提醒。

验收时至少要手动跑通：

1. 新建一个项目。
2. 在项目下新建一个待办，并设置 DDL 和备注。
3. 在项目下新建一个计划日程。
4. 完成该待办。
5. 在今日总结中看到完成记录并保存日志。
6. 关闭并重新打开安卓端，确认以上数据仍存在。
7. 导出 JSON 数据包。
8. 清空或切换测试数据后导入 JSON，确认项目、待办、日程和今日总结可以恢复。

### 基础导入导出

应支持：

- 导出 JSON 文件。
- 选择 JSON 文件导入。
- 导入前预览。
- 导入时校验 schema_version。
- 导入后提示结果。
- 不导出敏感凭据。

## 风险与注意事项

- 安卓端可能需要重构数据访问层，这是 v0.6 最大风险。
- 桌面端 sidecar 需要处理端口占用、进程退出和数据目录。
- 导入导出如果没有稳定 UUID，未来同步会更困难。
- 不要为了安卓端强行把现有后端塞进不适合的运行环境。
- 不要在 v0.6 同时追求提醒、同步、完整移动端体验。
- 打包体验版可以粗糙，但数据不能随意损坏。

## 已确认决策

- 桌面端优先采用 Electron。
- 桌面端继续复用 FastAPI + SQLite，通过 sidecar 或等价本地服务启动。
- 安卓端第一版可以接受功能不完整，但最初 MVP 已实现的核心功能不能缺少。
- 安卓端技术路线确认采用 Capacitor + WebView + SQLite 插件。
- v0.6.3 导入策略按“能可靠合并就追加/合并；做不稳就清空后导入并强提示”执行。
- v0.6 尽量给核心实体补 UUID，为未来同步铺路。
- v0.6 JSON 导出优先覆盖核心个人数据；ZJU 缓存和导入映射暂不作为强制范围。
- AI API Key、ZJU 密码、Pintia Cookie、Session、token 等敏感凭据不导出。
- 安卓端和桌面端允许先使用独立本地数据，不要求实时互通。
- v0.6 不做系统级提醒。
- v0.6 不要求正式发布，只需要存在一个可以由安卓端安装或加载的安装包。
- v0.6 不要求安卓端和桌面端 UI 完全一致，核心流程可用优先。

## 待确认问题

- 安卓端在实际接入 SQLite 插件时，如果现有前端 API 调用模式改动过大，需要由开发者提出最小适配方案。

## v0.6 实施状态与构建说明（2026-07-30）

### 版本落地

- v0.6.0：已加入 Electron 与 Capacitor 原型；Web/桌面继续走 FastAPI，Android 原生环境切换到 Capacitor SQLite。
- v0.6.1：已完成 Windows Electron + FastAPI sidecar 体验版。sidecar 使用随机回环端口，前端与 API 同源；Electron 退出时结束 sidecar。
- v0.6.2: Completed the Capacitor Android project, local SQLite data layer, debug APK, Android 36 emulator installation, cold-start persistence, and the MVP core-flow check.
- v0.6.3: Completed seven-entity JSON export, preview, atomic merge import, and Android -> FastAPI desktop -> Android round-trip verification with `schema_version: 0.6.0`.
- v0.6.4：已加入构建脚本、数据目录说明和已知限制。

### 桌面端构建

Windows PowerShell：

```powershell
.\scripts\build-desktop.ps1
```

如 Electron 官方下载通道不可达，可显式传入镜像：

```powershell
.\scripts\build-desktop.ps1 -ElectronMirror "https://npmmirror.com/mirrors/electron/"
```

构建顺序为：安装后端桌面依赖、PyInstaller 构建 `riji-sidecar.exe`、Vite 构建前端、electron-builder 生成 x64 portable。默认采用 `store` 压缩以提高体验版构建可靠性，因此单文件体积较大。产物位于：

```text
release/desktop/riji-desktop-0.6.0.exe
```

当前体验包未做正式代码签名，Windows 可能显示 SmartScreen 提示。

### Android 构建

要求：

- Node.js 22 或更高版本。
- JDK 21 或更高版本。
- Android SDK Platform 36，以及对应 Build Tools / Platform Tools。
- `ANDROID_HOME` 指向 Android SDK。

执行：

```powershell
.\scripts\build-android.ps1 -AndroidSdk "C:\path\to\Android\Sdk" -JavaHome "C:\path\to\jdk-21"
```

或在 Android Studio 中打开 `frontend/android`，等待 Gradle 同步后构建 debug APK。预期产物：

```text
frontend/android/app/build/outputs/apk/debug/app-debug.apk
release/android/riji-android-0.6.0-debug.apk
```

### 数据目录

- Windows Electron：`app.getPath('userData')/data/riji.db`，通常位于 `%APPDATA%/日迹/data/riji.db`。
- Android：SQLite 插件管理的应用内部数据库；卸载应用可能清除数据，卸载前应先导出 JSON。
- Web / Docker：继续由后端 `DATABASE_URL` 决定，未设置时为后端工作目录下的 `task_app.db`。
- Android 导出的 JSON 先写入应用缓存目录，再调用系统分享/保存面板；缓存文件不是长期备份位置。

### JSON 合并规则

- 导入包必须满足 `app: riji` 和 `schema_version: 0.6.0`。
- 项目、待办、日程、每日总结、日志模板、计时会话和重复规则按 UUID 合并。
- 相同 UUID 使用“导入包优先”；未出现在包中的本地数据保留。
- 日程关联待办、项目归属、完成待办等关系在包内使用 UUID，写入本机数据库时再映射为整数 ID。
- 每日总结额外以日期处理旧数据冲突。
- AI API Key 保留在各端 localStorage；ZJU 密码、Pintia Cookie、Session、token 和 ZJU 缓存不进入导出包。

### Experience-build verification (2026-07-30)

- Android 36 x86_64 emulator: installed and launched `com.riji.app`; exercised project, todo with hard DDL/reminder/category/focus/notes, planned schedule, completion, and daily-log flows.
- Cold-start persistence: after force-stop and relaunch, the project, two completed todos, linked schedule, and daily log were restored from app-private SQLite.
- JSON export: one project, two todos, one schedule, and one daily log. Credential scan found no API key, password, cookie, session, or token fields.
- Android -> desktop: an isolated FastAPI + SQLite sidecar previewed and imported all five records while preserving UUIDs and relationships.
- Desktop -> Android: preview reported five updates; atomic merge completed with zero creates and five updates, then survived another cold start.
- The APK is a debug-signed experience build, not a release build: package `com.riji.app`, version `0.6.0`, minSdk 24, targetSdk 36.

### Android v0.6 已知限制

- Android 36 emulator cold-start persistence and bidirectional JSON migration have passed. Physical-device matrix coverage, release signing, and store publication remain out of scope.
- 日程复杂拖拽在小屏上不是主要验收路径；创建、编辑和删除弹窗仍可使用。
- Android 与桌面使用独立本地数据库，只通过 JSON 手动迁移，不做账号或实时同步。
- 没有系统级提醒或通知。
- 在真机完成“关闭重开持久化”和双向手动迁移前，Android 体验版不能视为最终验收完成。
